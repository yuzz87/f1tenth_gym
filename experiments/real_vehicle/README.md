# Real Vehicle MPC/MPPI Simulation

This package is a simulation-only implementation for the current RC car.
It is intentionally separate from the F1TENTH benchmark controllers.

## Simulation completeness campaign

The reproducible campaign combines controller, course, pose source, plant model,
LiDAR condition, network condition, and random seed. The complete matrix is defined in
`config/simulation_campaign.yaml`.

~~~bash
PYTHONPATH=. gym_env/bin/python -m \
  experiments.real_vehicle.evaluation.simulation_campaign \
  --output-dir experiments/real_vehicle/results/simulation_campaign
~~~

The command writes raw CSV, grouped CSV/JSON, timing and error figures, and a Markdown
report. A bounded validation run is available as:

~~~bash
experiments/real_vehicle/run_simulation_validation.sh
~~~

The plant profiles cover ideal, nominal, and degraded actuator behavior. LiDAR profiles
cover ideal and distance-dependent noisy scans with jitter, burst dropout, and mount
errors. Network profiles cover normal traffic, delay jitter, dropout bursts, and a
temporary outage.

## Complete offline pipeline

When the real vehicle is unavailable, the saved `small_test_area_03` map and recorded
LiDAR/odometry can still be used. The offline pipeline runs Pure Pursuit, MPC, and MPPI
on the saved map, evaluates ideal/noisy/delayed LiDAR, replays all usable real sensor
trials, and generates CSV, JSON, Japanese figures, and an English PNG-only folder.

~~~bash
experiments/real_vehicle/run_offline_pipeline.sh \
  --output-dir experiments/real_vehicle/results/offline_complete_pipeline
~~~

Use `--smoke` for a short contract check. No ROS graph, GPIO, pigpio, PWM, motor,
steering servo, or networked Raspberry Pi is used by this command.

## Presentation controller comparison

Use the dedicated experiment when MPC and MPPI must be compared with data generated by
the same code revision and conditions. It runs one circular lap for three matched seeds,
saves every trajectory, and creates SVG figures plus a Japanese Markdown report without
requiring Matplotlib.

~~~bash
PYTHONPATH=. gym_env/bin/python -m \
  experiments.real_vehicle.evaluation.presentation_experiment
~~~

The default output is
`results/2026-07-21_presentation_controller_comparison/`. Existing output is never mixed
silently; pass `--overwrite` to replace a previously generated batch. Use
`--seeds 123 --max-steps 20` for a bounded smoke check. This experiment is simulation
only and rejects configurations that enable hardware output.

## State and input

```text
state = [phi, x, y, psi]
input = [v, omega]
```

`omega` is steering-angle rate [rad/s], not yaw rate. The model uses the
wheelbase `0.25 m` and SI units throughout.

## Quick start

From the repository root:

```bash
gym_env/bin/python -m experiments.real_vehicle.evaluation.straight_test \
  --controller mpc --output experiments/real_vehicle/results/straight_mpc.csv

gym_env/bin/python -m experiments.real_vehicle.evaluation.circle_test \
  --controller mppi --output experiments/real_vehicle/results/circle_mppi.csv

gym_env/bin/python -m experiments.real_vehicle.evaluation.preflight
```

No GPIO, pigpio, PWM output, ROS node, or real hardware is used by these
commands.

## Package layout

- `config/`: actual vehicle parameters and limits
- `models/`: four-state bicycle model
- `adapters/`: steering conversion, ESC duty safety limits, and command diagnostics
- `controllers/`: two-input MPC and MPPI
- `evaluation/`: straight, circle, LiDAR, comparison, and preflight runs
- `gui/`: interactive pyglet simulation view
- `localization/`: virtual LiDAR and map-based pose estimation
- `tests/`: focused unit tests
- `results/`: generated CSV files
- `integration_ws/`: Python・ROS 2実機接続、安全監視、Mock Vehicle

## GUI

Launch the standalone simulation window from the repository root:

```bash
PYTHONPATH=. gym_env/bin/python \
  -m experiments.real_vehicle.gui.run \
  --controller mppi --scenario straight
```

Available scenarios are `straight`, `circle`, and `localized`. LiDAR
noise, dropout, and delay can be added with `--noise-std`,
`--dropout-probability`, and `--delay-s`. Press `Space` to pause or resume,
`R` to reset, `+/-` to zoom, and `Esc` or `Q` to close and save the CSV.

For a harder localization view, add `--complex-map` and initial pose errors
with `--initial-x-error`, `--initial-y-error`, and
`--initial-heading-error`.

The GUI uses a compact cyan ring to indicate the 360-degree LiDAR around the
vehicle. Individual beam lines are intentionally hidden to keep the view
readable; the scan data is still used by the localization and control logic.

The GUI is simulation-only. It does not use GPIO, pigpio, PWM, ROS, or real
hardware output.

## ROS 2 integration

Phase 1〜6のROS 2接続実装は次にある。

```text
experiments/real_vehicle/integration_ws/src/real_vehicle_integration/
```

実装済みの範囲:

- `/scan`、`/odom`、TFを発行するMock Vehicle
- LiDAR Localization Node
- MPC/MPPI Controller Node
- arm/start/stopとwatchdogを持つSafety Node
- 独立watchdogとMock PWMを持つActuator Node
- CSV LoggerとROS graphスモーク検査

標準設定では実PWM出力を禁止している。ビルド・起動手順は
`integration_ws/src/real_vehicle_integration/README.md`を参照する。

現在の32-bit Raspbianを維持する実機構成では、PiへROS 2を導入せず、
`pi_agent/`のスタンドアロンPython UDP Agentを使用する。Piへの配置と安全な
ドライラン手順は`pi_agent/README.md`にまとめている。

## Legacy ROS2 virtual sensors

After sourcing a ROS2 Foxy environment, the virtual sensor node publishes
`/scan`, `/odom`, and `map -> odom -> base_link -> laser` TF:

```bash
source /opt/ros/foxy/setup.bash
PYTHONPATH=. gym_env/bin/python \
  -m experiments.real_vehicle.ros2.virtual_sensor_publisher \
  --duration 10
```

This standalone publisher remains available for a minimal sensor contract check.
The full integration pipeline uses the ROS 2 package described above.

## Speed evaluation (independent of encoder duty calibration)

The measured speed range can be compared without hardware:

```bash
PYTHONPATH=. gym_env/bin/python \
  -m experiments.real_vehicle.evaluation.speed_sweep \
  --speeds 0.30,1.0,3.0,6.1 \
  --controllers mpc,mppi \
  --scenario straight
```

The command temporarily raises the simulation speed limit to each requested
case and writes a comparison CSV and summary JSON. These are virtual model
speeds; they are not derived from encoder data or a hardware duty calibration.

## Duty boundary evaluation (simulation only)

The real-vehicle duty policy is:

```text
stop/idle: 10.30%
reliable start: 10.16%
hardware forward-side limit: 10.10%
```

The following command checks the safe clamp and an explicit experimental mode.
It never sends GPIO, pigpio, PWM, or any other hardware output.

```bash
PYTHONPATH=. gym_env/bin/python \
  -m experiments.real_vehicle.evaluation.duty_sweep \
  --duties 10.30,10.20,10.16,10.10,10.00,9.90,9.70 \
  --virtual-speed-max-mps 6.1
```

In safe mode, values below `10.10%` are clamped to `10.10%`. The experimental
column permits them only for simulation inspection. The result is a duty
boundary check, not a claim that a particular duty produces a measured ground
speed.

For an initial-error LiDAR test:

```bash
PYTHONPATH=. gym_env/bin/python \
  -m experiments.real_vehicle.evaluation.localized_control_test \
  --controller mppi --steps 100 --complex-map \
  --initial-x-error 0.20 --initial-y-error -0.10 \
  --initial-heading-error 0.10 --noise-std 0.01 \
  --dropout-probability 0.10 --delay-s 0.05
```
